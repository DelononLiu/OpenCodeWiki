# Wiki 实体化改造设计

## 背景

当前 wiki 存在以下问题：
- 模块目录组织文档，背离开发者碎片化查阅的真实场景
- 层级侧边栏使用率低、维护负担重
- 缺乏实体间关联，知识体系是线性的不是网状的

## 设计原则

1. **搜索为中心** — 搜索框是最高频入口，检索结果优先推送实体条目
2. **实体为最小单元** — 每个业务概念是一个独立实体页面，不按目录划分
3. **双向引用** — 实体间通过上下游关系构成网状知识体系
4. **目录树保留** — overview/架构/构建部署等系统性文档保留在目录树中，与实体互补

## 实体页面

### 内容来源

三阶段生产流程：

| 阶段 | 动作 | 权威性标注 | 方式 |
|------|------|-----------|------|
| **Phase 1** | LLM 根据 codebase-memory-mcp 数据生成骨架 | "AI 生成初版" | 自动 |
| **Phase 2** | 人工修正骨架（概念边界、补充遗漏、修正错误） | "已校准" | 人工 |
| **Phase 3** | LLM 基于已校准骨架填充细节 | "已填充" | 自动 |

### 实体页面结构

```
┌──────────────────────────────────────┐
│  实体名    权威性: [已校准]           │
│                                      │
│  定义：一句话描述                    │
│                                      │
│  ── 涉及代码 ──                     │
│  · file.ts:42  (class XxxManager)   │
│  · file.ts:155 (function handleXxx) │
│                                      │
│  ── 上游/下游 ──                    │
│  上游（依赖）                       │
│  · [实体A] → [当前实体]             │
│  下游（被调用）                      │
│  · [当前实体] → [实体B]             │
│                                      │
│  ── 详情 ──                         │
│  (LLM 填充的叙事型描述 + mermaid 图) │
│                                      │
│  ── 局部关系图 ──                   │
│  [实体A] ←→ [当前实体] ←→ [实体B]   │
│            ↕                        │
│          [实体C]                    │
│  (限制 1-2 层关联，不作为全屏页面)   │
└──────────────────────────────────────┘
```

## 搜索

- 搜索范围覆盖：实体名、实体定义、涉及文件路径
- 搜索结果排序：实体名匹配 > 定义匹配 > 文件匹配
- 历史问题搜索作为补充项（从 QA 会话中匹配）

## 目录树侧边栏

- 保留 overview、架构总览、构建部署等系统性文档
- 不展示实体列表（实体通过搜索访问）
- 侧边栏底部展示当前实体的相关实体列表（做导航辅助）

## 与现有 wiki 的迁移

1. **新系统与现有系统并存** — openwiki 生成的文档（quickstart/architecture/operations）保留在目录树中
2. **实体系统独立** — 实体页面另有存储位置（`.codegraph/wiki/entities/`）
3. **openwiki 继续使用** — 用于生成目录树中的系统性文档，实体系由新流程管理
